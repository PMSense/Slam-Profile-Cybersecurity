Module 01 · Week 1 tutorial

Model selection & the bias-variance tradeoff

The idea every later project keeps coming back to: the goal isn't the model that fits training data best, it's the smallest one that generalizes.

Starting point: a noisy sample of a true cosine function, fit with polynomial regression at three complexities — degree 1, 4, and 15 — chained together with PolynomialFeatures + LinearRegression in a single sklearn Pipeline.

Underfit — degree 1

Only 2 parameters. Too simple to capture the curve — poor fit even to the training data it saw.

Overfit — degree 15

Fits the observed noisy points almost perfectly — and is exactly why it won't generalize to new data.

"We are interested in the smallest model that fits our data the best… the degree 4 model appears to be a good blend of small model size and good generalization."

This framing — smallest-model-that-generalizes — is the thread running through every later project: the parameter-budget search in Module 06, the L1 feature-selection pass in Module 05, and the "why did the poisoned model break so easily" analysis in the Module 07 capstone all reduce to the same question.

Module 02 · Week 1, "Tour de Classifier"

Seven classifiers, one non-linear dataset

The fastest way to build intuition for when a model family fits a problem: fit all of them to the same data and look at where each one's decision boundary breaks.

Dataset: a classic 118-row, 2-feature binary QA-test set with a non-linear (curved, near-concentric) class boundary. Every classifier trained on the same raw x,y features, evaluated on training accuracy, with a shared decision-boundary visualization (probability = 0.5 contour, misclassified points circled in red).

ClassifierAccuracyBoundary shape
SVM — RBF kernel84.7%Flexible, non-linear — best fit for this data
Naive Bayes (Gaussian)74.6%Probabilistic, independence-assumption — solid despite the assumption being technically violated
SVM — polynomial kernel66.1%Non-linear, but a worse fit than RBF for this shape
SVM — linear kernel55.1%Straight-line boundary — structurally can't capture curved clusters
Logistic Regression54.2%Linear boundary — same limitation
Perceptron50.8%Linear, no probability estimate
SGD Classifier (hinge loss)39.8%Linear — worst performer, below what a coin flip would suggest on this near-balanced set

The pattern is the lesson: every linear-boundary method clusters in the low-50s/high-30s; every non-linear method does meaningfully better, and the most flexible kernel (RBF) wins outright — because the data itself isn't linearly separable.

Module 03 · Project 1

MNIST digit classification with k-NN

70,000 handwritten digits, a lazy learner, and a lesson in why a straight line was the wrong tool for a learning curve.

k-Nearest Neighbors swept at k = 1, 3, 5, 7, 9 on MNIST (784 pixel features, normalized to [0,1]); best result at k=1, 88.4% dev accuracy, roughly flat across k. Per-digit analysis (1-NN classification report): digit 8 was hardest to classify (F1 = 0.80); digit 0 easiest (F1 = 0.95). Confusion matrix: 4 was most often confused with 9 — the single most common error pair, consistent with visual similarity.

The training-size experiment, and where a linear model lied

Accuracy vs. training-set size (100 → 25,600 examples) rose from 70.2% to 96.3% — a diminishing-returns curve. Fitting a plain linear regression to accuracy-vs-size produced nonsense: predicted accuracies above 100% for larger training sizes. The fix — log-transforming size and logit-transforming accuracy before regressing, then inverting both transforms — respected two real constraints a straight line ignores: the relationship is curved, and probabilities can't exceed 1.

k-NN's cost profile showed up exactly as expected: training time near-zero (it's a lazy learner — no real "fit" step), while prediction time grew substantially with training-set size, since every prediction compares against the entire stored dataset.

Module 04 · Project 2

Naive Bayes, feature engineering, and knowing when it doesn't help

Same MNIST digits, three Naive Bayes variants, a hand-built blur filter, and a hard lesson: engineered features lost to raw pixels.

Model variantAccuracyNote
BernoulliNB (binarized pixels)81.4%Best-suited NB variant for this binary-ish data
MultinomialNB (3-level pixels)80.7%Extra "gray" level didn't help — count-based assumptions mismatch intensity data
GaussianNB, default59.3%Broke on zero-variance pixel features
GaussianNB, var_smoothing=0.0581.6%Regularization fixed the numerical instability
1-NN + custom blur filter (train-only)90.4%Best result in the notebook — blurring the training set forces generalization past pixel noise
1-NN + blur (dev-only)87.5%Worst blur variant — train/dev distribution mismatch, a preview of exactly the domain-shift problem covered in Module 04 of the Stanford guide
Hand-engineered features

Block-sum (49 features) and row/column-sum (56 features) aggregations, tried as a dimensionality-reduction alternative to raw pixels: 72.6% and 66.4% respectively — both worse than the 83.0% baseline on raw pixels.

The lesson

Aggregating pixels destroyed the fine-grained stroke and positional information the model actually needed to tell similar digits apart. Feature engineering isn't automatically an improvement — it's a dimensionality-reduction/information tradeoff that has to be checked, not assumed.

A calibration check on the tuned BernoulliNB model (Laplace smoothing α=0.001, found via 5-fold GridSearchCV) found it overconfident — accuracy rose with predicted-confidence bucket as expected, but consistently trailed the stated confidence, which is a documented characteristic of Naive Bayes' independence assumption rather than a bug.

Module 05 · Project 3

Text classification: sparse features, real tradeoffs

20 Newsgroups posts, four topics, and the moment a model's biggest error mode turned out to be "reacting to keywords instead of context."

4-way topic classification (alt.atheism, comp.graphics, sci.space, talk.religion.misc) on 2,034 training posts. Baseline word-unigram vocabulary: 26,879 features, sparse (0.36% density).

ModelBest F1Note
k-NN (best k=7)0.44Fails on high-dimensional sparse text — distance stops being meaningful
Logistic Regression (unigrams)0.70Best at C=0.1; regularization strength directly tracked weight magnitude
Multinomial Naive Bayes0.79Best model on raw counts — its independence assumption acts as implicit regularization on sparse text, where per-word logistic regression is more prone to overfitting
Logistic Regression + TF-IDF0.76Down-weighting common words beat raw counts
Where the errors actually came from

Using an "R-ratio" (confidence in the wrong label ÷ confidence in the true label) to surface the worst misclassifications: a talk.religion.misc post asking for an FTP site hosting the Book of Mormon was classified comp.graphics at 99.4% confidence — the model reacted to "FTP" and file-format vocabulary, not the actual topic. A custom preprocessing pipeline (stemming, digit normalization, stripped punctuation) cut the vocabulary by 39% while raising F1 from 0.7085 to 0.7285 — proof that most of that 27k-word vocabulary was noise, not signal. Adding bigram context (to catch phrases like "no God" vs. "God") fixed the mechanism behind these errors but only moved F1 by +0.0001 — validated the hypothesis, but the affected cases were rare.

A separate L1-regularization pass used as a feature-selection tool cut the vocabulary to 212 words (from 26,879) while barely moving F1 (0.6951 vs. 0.7085 baseline) — evidence that a small, well-chosen subset of words carries almost all the classification signal.

Module 06 · Project 4

Unsupervised learning: PCA, k-means & Gaussian mixtures

Building a working classifier without ever telling the model which mushrooms are poisonous — and then beating the "obvious" version of it under a hard parameter budget.

126 binarized mushroom features (cap shape, odor, gill color, habitat, etc.) compressed via PCA: the first 2 components retain 29.7% of variance, but that alone is enough to visually separate poisonous from edible clusters. A generative classifier was then built with no labeled training in the usual sense — two separate Gaussian Mixture Models were fit, one on the 2D-projected poisonous examples, one on the non-poisonous — and a test point classified by comparing which GMM assigns it higher likelihood.

Unconstrained model

2 PCA dimensions, 4 GMM components, full covariance: 94.93% test accuracy.

Budget-constrained search (≤50 parameters)

Grid search across PCA dimensions × GMM components × covariance type, hand-deriving the parameter-count formula for each covariance type. Best: 4 PCA dims, 3 components, tied covariance, only 40 parameters — accuracy 96.98%, beating the unconstrained model with fewer parameters.

The same bias-variance lesson from Module 01 resurfaces here in its most concrete form yet: more model complexity (full covariance, more components) was strictly worse than a smaller, better-constrained model — not just simpler for its own sake, but actually more accurate.

Module 07 · Capstone projectAI Security

Poisoning — and patching — a network intrusion detector

Cyber 207: AI/ML in Cybersecurity, UC Berkeley MIDS. Team project with Ian McGuffin and Colin van Ree — the piece of coursework that's a direct, hands-on counterpart to the data-poisoning theory in the Stanford AI Security guide.

The problem

Modern network intrusion detection systems (NIDS) increasingly rely on ML, which makes them entirely dependent on training-data quality. If an attacker can get into the data supply chain — a compromised labeling process, an insider, a poisoned feedback loop — and relabel real malicious traffic as "safe," they create a permanent blind spot in the security system, without ever touching the model's code.

Setup: dataset, model, and a deliberately sequestered attack class

Built on the CIC-IDS-2017 network traffic dataset (Canadian Institute for Cybersecurity) — 18 CSVs covering benign traffic plus attack types spanning DoS (GoldenEye, Hulk, Slowhttptest, Slowloris), DDoS, botnet, port scan, brute force (FTP/SSH), web SQL injection, XSS, and Heartbleed. A RandomForestClassifier (100 trees, balanced class weights) was trained on a stratified 70/30 split (150,367 train / 64,443 test rows, 121 features), after dropping IP/port/timestamp fields specifically to prevent the model from overfitting to attacker identity rather than traffic behavior. Six DoS-family attack types were deliberately held out entirely from training — 470,882 rows sequestered as a stand-in for a "zero-day" attack the model had never seen.

The attack: label flipping, "boiling frog" style

Rather than poisoning everything at once, the team incrementally increased the poison rate to find the model's actual breaking point — an integrity/backdoor attack (targeted at one traffic type) rather than a blunt availability attack on the whole system. At each rate, a sample of the sequestered DoS traffic was relabeled from Attack (1) to Benign (0) — the underlying traffic features were left completely real, only the label was corrupted — mixed into the clean training set, and a fresh model retrained from scratch.

The results
Base model (never trained on this DoS class)
7%
Poisoned at 1% label-flip rate

Poisoned at 5–30% label-flip rate

After defense: retrained on verified labels

Recall on the held-out DoS ("zero-day") traffic at each stage.

The collapse wasn't gradual — it was immediate. At just 1% of the target class poisoned, detection fell from an already-weak 7% baseline to 0.01%; by 5% it flatlined completely and stayed at exactly 0.00% all the way to 30%. The team's own explanation is the more interesting finding: because the base model already had low confidence on this unfamiliar traffic pattern (only 7% baseline recall), it had no strong decision boundary defending that territory — so it took only a small poisoned "nudge" to push detection to zero. A model that's already uncertain about a class is disproportionately easy to poison on exactly that class.

The defense

Data provenance plus trusted retraining: relabel the corrupted DoS traffic back to its correct (Attack) label using a verified source, mix it back into a clean training set, and retrain. Recall was fully restored to 100% — proof that the fix isn't a smarter model, it's a smarter data pipeline. The team's broader recommendation leaned on Zero Trust principles: verify explicitly, use least-privileged access, and assume breach — applied to training data itself, not just network access.

Why this generalizes beyond one project

The team's own literature review connected the finding to current LLM-poisoning research (Souly, Rando et al., 2025), which found that poisoning frontier LLMs requires a near-constant, small absolute number of poisoned samples — largely independent of model or dataset size. The pattern this capstone reproduced at NIDS scale (a small fraction of poisoned data causing a disproportionate, non-linear collapse) is the same shape of vulnerability showing up from a random forest classifier all the way up to billion-parameter language models — which is exactly the throughline back to the "no strong defense so far" framing in the Stanford AI Security guide's adversarial-examples module.

Reference

Glossary

Terms worth using precisely when this coursework comes up.

Bias-variance tradeoff
Underfitting (too simple, high bias) vs. overfitting (too flexible, high variance) — the smallest model that still fits well generalizes best.
Lazy learner
A model (like k-NN) with near-zero training cost that pushes all the computational work to prediction time.
Calibration
Whether a model's stated confidence matches its actual accuracy — Naive Bayes here was consistently overconfident.
TF-IDF
Term Frequency–Inverse Document Frequency — down-weights common words, up-weights topic-distinctive ones, vs. raw word counts.
L1 feature selection
Using L1-regularized model weights (which zero out unneeded features) to prune a vocabulary before refitting a cleaner model.
Generative classifier
Classifies by comparing which class's learned data distribution a new point is more likely to have come from (vs. discriminative models, which learn a direct decision boundary).
Covariance type (GMM)
Spherical / diagonal / tied / full — how much shape flexibility each Gaussian mixture component gets; "tied" shares one shape across all components.
Label flipping
A data-poisoning technique that corrupts a label while leaving the underlying features authentic — the model learns the wrong association from real data.
Zero-day (in this context)
An attack class deliberately withheld from training, used as a stand-in for a genuinely novel attack the model has never seen.
Data provenance
Verifying the origin and integrity of training data/labels — the actual defense that restored recall to 100% in the capstone.
Applying this

Ready-made framings for a conversation

Pairs directly with the Stanford AI Security guide's talking points — that one is the theory, this is the hands-on proof.

If someone asks "have you actually built anything, not just studied the theory?"

Lead with the capstone: built a working ML-based intrusion detector, then attacked it myself with a label-flipping data-poisoning campaign, watched detection collapse from an already-weak 7% to a complete 0% at just 1% poisoning, and then fixed it — recall fully restored to 100% — with a data-provenance and retraining pipeline. Attack and defense, both hands-on, both measured.

If someone asks "why does a small amount of poisoned data cause such a big effect?"

Because a model with weak prior confidence on a class has no strong decision boundary defending it — poisoning doesn't have to overpower a confident model, it just has to nudge an already-uncertain one. That's the exact mechanism the capstone measured, and it's the same shape of vulnerability that shows up in LLM-poisoning research at a completely different scale.

If someone asks about ML fundamentals, not just security

Point to the classifier bake-off (7 model families on one dataset, RBF-SVM's 84.7% vs. linear SGD's 39.8%) and the mushroom-toxicity project (a 40-parameter budget-constrained GMM beating an unconstrained, higher-complexity model) — both are concrete, numeric proof of knowing when a model's complexity is helping versus just adding risk.
