Module 01

Overview & overall execution plan

A systematic, phased build — each control layered on the last to reach comprehensive coverage, not a single feature demoed in isolation.

This hands-on project documents a series of comprehensive security architectures conducted within an Amazon Web Services (AWS) environment, focusing on foundational principles and advanced techniques in cloud security engineering. The core objective was to establish a multi-layered, Defense-in-Depth security posture, moving beyond theoretical knowledge to the practical, hands-on implementation of an end-to-end, robust, and secure application ecosystem.

The work explores the Principle of Least Privilege (PoLP) applied across identity and networking; data-at-rest encryption using AWS KMS; data-in-transit encryption using TLS; secure network segmentation via a VPC; Infrastructure as Code (IaC) with Terraform for repeatable, version-controlled deployments; and automated threat detection and response workflows. By simulating real-world scenarios — including intentional misconfigurations — and auditing against industry best practices, the project demonstrates a complete lifecycle approach to building, securing, and continuously monitoring cloud infrastructure.

Module 03 · 4.1

Identity management and privilege control

Least privilege proven two ways: by demonstrating it correctly, then by intentionally breaking it and catching the break.

Principle of Least Privilege (PoLP)

This workstream established foundational security by focusing on PoLP. We created the user John_Developer within the Berkeley_Developers group. The correct implementation of PoLP was demonstrated by assigning the developer-s3-app-logging-prod policy, narrowly scoped to grant only List, Get, and Put S3 actions on a single, specific application log bucket.

Users, policies, and Cloudsplaining
The intentional violation

We intentionally violated PoLP by creating an overly permissive policy (s3:* on *), simulating a security flaw that could lead to lateral access to sensitive financial data.

The catch

The open-source auditing tool Cloudsplaining successfully detected the high-risk misconfiguration, leading to remediation of the policy and enforcement of strict access controls.

Module 04 · 4.2

Data security and encryption

Data-at-rest protection through layered access control — accessible only to a user with both the right S3 permission and the right key permission.

Data-at-rest protection

The objective was to ensure data-at-rest protection through layered access control, making the data accessible only by users who had both the necessary S3 permissions and the authorization to use the specific AWS Key Management Service (KMS) key.

Key management — SSE-KMS and key policies

We created a symmetric customer-managed key named LabKey and enforced Server-Side Encryption (SSE-KMS) as the default for a target S3 bucket. Crucially, the Key Policy for LabKey was configured to explicitly grant John_Developer key-usage permissions. This design ensures access to the encrypted data is governed by two independent controls: the S3 Bucket Policy (resource permissions) and the KMS Key Policy (cryptographic permissions).

Module 05 · 4.3

Secure networking design

A "zero-exposure" model — private resources reachable without a single inbound firewall rule opened for management access.

Defense-in-depth networking

A robust network architecture was established using a Virtual Private Cloud (VPC), segmented into a Public Subnet (for the internet-facing web server) and a Private Subnet (for the sensitive/internal database), ensuring strong segmentation and controlled routing.

VPC, subnets, routing, and access controls

Routing was tightly controlled: the Private Subnet routed all outbound traffic through a NAT Gateway, blocking all direct inbound access. Network Security Groups were applied following PoLP. A key security enhancement was the use of an IAM Role with AWS Systems Manager (SSM) to securely manage the private EC2 instance, implementing a "zero-exposure" security model that eliminated the need for a traditional bastion host.

Module 06 · 4.4

Secure application deployment and hardening

Infrastructure as Code, encrypted transit, and a supply-chain scan — deployment treated as a security surface in its own right.

Secure deployment and supply chain

A containerized Apache web application was deployed on an EC2 instance using Terraform for full Infrastructure as Code (IaC) management. The focus was on securing the deployment with proper network access controls, securing data-in-transit, and ensuring software supply-chain integrity.

IaC, TLS, IAM roles, and Trivy scanning

Data-in-transit was secured by configuring TLS/HTTPS using a Let's Encrypt certificate. Security of the application host was enhanced by assigning an IAM Role to the EC2 instance, allowing it to request temporary, automatically rotated credentials. The Trivy tool was used to scan the container image for known supply-chain vulnerabilities.

Module 07 · 4.5

Operational visibility and auditing

Default configurations are rarely audit-ready — Prowler found the gap between "deployed" and "actually hardened."

Audit trail and security assessment

The primary objective was to deploy, verify, and security-audit AWS CloudTrail — the foundational service for governance, compliance, and incident response — to ensure a reliable audit trail for all API activities.

CloudTrail deployment and Prowler audit

The CloudTrail service was deployed using Terraform, then subjected to a security audit using the Prowler tool. The audit revealed that the default configuration lacked essential security hardening — specifically failing to enable log file validation and KMS encryption — necessitating deliberate configuration changes beyond the typical out-of-the-box settings.

Module 08 · 4.6

Automated threat detection and response

A serverless remediation pipeline that turns a malware finding into a quarantined object and a notification, with no human in the loop.

Serverless remediation pipeline

This workstream demonstrated the end-to-end deployment of an automated, serverless malware remediation pipeline, aiming to deliver a low-cost, automated threat detection and response capability.

GuardDuty, EventBridge, and Lambda automation

AWS GuardDuty was enabled with the S3 Malware Protection feature. The event-driven architecture was built using Amazon EventBridge to listen for malware findings, which automatically triggered a Python AWS Lambda function. This function performed automated two-part remediation: copying the malicious object to a quarantine bucket, then deleting it from the source — drastically reducing the Mean Time to Respond (MTTR).

Module 09 · 4.7

Advanced access control: Zero Trust

Access permitted only when a user has the correct least-privilege role and a verified device posture — never identity alone.

The final workstream implemented a modern Zero Trust access model, requiring explicit verification before granting access. Access control logic was defined in a "default deny" Open Policy Agent (OPA) policy using the Rego language. The policy enforced that access was permitted only when a user had the correct least-privilege role and a verified device posture.

Module 10 · Reflection

Reflection & lessons learned

The cumulative experience across these workstreams reinforced several critical, transferable principles for any professional cloud security engineering effort.

Core security principles in practice

PoLP was the most central and profound theme. Implementation is a continuous auditing effort, not a one-off configuration — the intentional violation confirmed that its failure creates a catastrophic risk of lateral movement to sensitive data, making continuous monitoring (like Cloudsplaining) essential for enforcement. The project also reinforced Defense-in-Depth: a secure architecture requires independent, overlapping controls across identity, network, and application layers.

Operational and automation complexity

Infrastructure as Code (Terraform) was critical for consistency and repeatability, complemented by the GuardDuty-Lambda pipeline, which demonstrated that serverless automation can drastically reduce MTTR from hours to seconds. The true complexity lies in the careful, layered configuration of permissions — the smallest misconfigured policy can halt the entire workflow, requiring exhaustive, end-to-end testing. The network workstream showed the clear benefit of a "zero-exposure" approach using IAM roles with AWS Systems Manager (SSM) for private resource access, eliminating the need for security-compromising inbound firewall rules.

Visibility gaps and configuration pitfalls

Working with CloudTrail demonstrated that default cloud configurations are often insufficient for true security and compliance — the Prowler audit revealed that a comprehensive audit capability requires deliberate configuration beyond the out-of-the-box settings, specifically enabling log file validation and KMS encryption. A significant and costly lesson: enabling AWS IAM Access Analyzer triggered immediate billing based on the number of resources analyzed per month — a reminder of the non-obvious, non-linear cost models in the cloud, and the need to fully vet pricing documentation before activating any new service.

Advancing access control

The Zero Trust effort confirmed that an effective architecture requires both verified identity and verified device posture. The implemented model is an early stage; for production maturity, the system should integrate dynamic verification using tools like GuardDuty and IAM Access Analyzer to keep policies robust and adapt to real-time user behavior — continuous verification beyond a static rule set.

Appendix

Project technologies, security tools, and their roles

The core technologies and security tools used across the project, and their specific role in implementing the Defense-in-Depth posture.

AWS IAM
Core service for managing users, groups, and permissions — used to implement and test PoLP via tightly scoped policies and roles.
AWS KMS
Created and managed symmetric customer-managed keys (LabKey); enforced layered access control for data-at-rest protection (SSE-KMS).
AWS S3
Storage target for application logs and sensitive data; enforced SSE-KMS encryption and served as the target for automated malware scanning/quarantine.
AWS VPC
Core network service establishing a secure, segmented architecture with public/private subnets, enforcing Defense-in-Depth.
AWS Systems Manager (SSM)
Enabled secure access to private EC2 instances via IAM roles — zero-exposure management with no bastion host required.
AWS CloudTrail
Deployed via IaC to create a consistent audit trail for governance, compliance, and incident response by logging all API activity.
AWS GuardDuty
Threat detection service with S3 Malware Protection — scanned uploaded files for malware and triggered the automated response workflow.
Amazon EventBridge
Event-driven service configured to trigger the system by listening for GuardDuty malware findings.
AWS Lambda
Serverless Python function executing automated response logic: quarantining malicious files and sending alerts.
Amazon SNS
Sent detailed notifications (via email) to the security team after automated remediation.
Terraform
IaC tool used to provision the full cloud environment (VPC, IAM, GuardDuty, Lambda, CloudTrail, etc.) consistently and repeatably.
Cloudsplaining
Audited IAM to detect overly permissive policies (e.g. s3:* on *) that violate PoLP.
Prowler
Audited CloudTrail against AWS best practices, identifying missing hardening requirements such as log file validation.
Let's Encrypt / Certbot
Issued and automatically renewed TLS certificates to ensure encrypted data-in-transit.
Trivy
Scanned the application's container image for supply-chain vulnerabilities to ensure software integrity.
Open Policy Agent (OPA)
Policy engine enforcing Zero Trust access controls using identity and device-posture checks.
Rego
Policy language for OPA, defining fine-grained access rules for the Zero Trust implementation.
KICS
Scanned Terraform code for vulnerabilities and misconfigurations before deployment.
